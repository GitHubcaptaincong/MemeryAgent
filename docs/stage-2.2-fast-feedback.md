# 阶段 2.2：短内容快速记录与持续反馈

## 问题

原实现让短内容和长学习材料执行相同的多轮 Agent 流程。真实菜式记录需要约 37 秒，早期版本甚至接近一分钟；模型调用期间界面缺少明显反馈。

## 产品语义

“记录完成”和“AI 整理完成”现在是两个时间点：

1. 原文先写入数据库，界面立即显示记录回执。
2. AI 在后台生成可审阅草稿。
3. 用户确认草稿后，才进入独立的长期记忆审批流程。

因此模型超时或自动重试不会造成原始记录丢失。

## 快速通道

默认阈值为 600 字。短内容直接作为不可信数据传给模型，只允许调用 `quick_generate`：

- 模型输出 1–2 个紧凑知识单元。
- 紧凑结构只包含概览、标题、解释、要点、问题、答案和逐字证据。
- 应用代码补全完整产品字段并定位唯一证据区间。
- 完整草稿继续经过 `schema_validate`。
- 一次校验通过后直接落草稿，不再请求模型重复提交。
- 校验失败时才进行下一轮模型修正。

快速通道使用 `reasoning=none` 和 2,500 输出 Token 上限。超过阈值的材料仍使用完整 Agent 工具流程。

## 用户可见反馈

- 点击后前端立即进入运行态，不等待 API 返回才显示状态。
- 原文保存完成后显示字符数和保存耗时。
- 服务端 SSE 在没有新持久化事件时，每 2 秒发送 `progress.pulse`。
- 运行面板展示当前处理通道、当前动作、累计耗时、最近反馈时间、工具和校验结果。
- Provider 超时、退避重试和过期租约接管都有用户可见摘要。

界面不展示模型原始隐式思维链。所谓“思考过程”限定为可审计的计划、动作、工具输入输出摘要、校验结论和错误恢复原因。

## 真实测量

同一份番茄炒蛋短内容：

| 指标 | 优化前 | 优化后 |
|---|---:|---:|
| 原文持久化 | 未单独展示 | 79 ms |
| API 完整受理 | 未单独展示 | 97 ms |
| AI 草稿完成 | 37.1 s | 11.4 s |
| 业务工具调用 | 1 | 1 |
| 输出 Token | 1,118 | 602 |

页面自动化复测另一份菜式时，记录回执在 116 ms 出现，草稿在 9.2 秒出现。CLIProxy 的最小模型请求实测约 5.7 秒，因此当前无法承诺最终 AI 结果 4 秒内完成；产品承诺是立即保存、首反馈小于 4 秒、运行期间每 2 秒有新状态。
