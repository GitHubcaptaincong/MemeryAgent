# 阶段 2.1：模型质量与可靠性

## 目标

本阶段解决真实模型接入后出现的两个问题：

1. 模型自行计算证据字符区间，容易反复校验并消耗 Token。
2. 模型服务超时或 Worker 中断后，任务会直接失败或无法被重新接管。

不在本阶段持久化模型隐式推理、Provider 原始 reasoning item 或完整对话回放。

## Agent 生成流程

```text
source_read
  -> source_locate_quotes
  -> schema_validate
  -> 证据错误时重新定位
  -> 其他结构错误时直接修正并重新校验
  -> submit_draft
  -> awaiting_user
```

每个阶段只向模型暴露当前允许调用的一个函数工具，并使用 `tool_choice=required`。
最终草稿必须与最后一次校验通过的草稿具有相同的规范化哈希。

## 原文证据定位

`source_locate_quotes` 接收 1–30 条逐字引用，每条最多 500 字，返回零基、左闭右开的字符区间。

- 唯一出现：返回权威 `start_char` 和 `end_char`。
- 多次出现：标记为 `ambiguous`，要求模型选择更长的上下文。
- 未出现：标记为 `not_found`，要求模型从 `source_read` 结果重新逐字复制。
- 工具事件摘要只记录请求数、成功数和未解决数，不把引用正文写入公开事件流。

CLIProxy 当前接受的严格函数 Schema 子集不包含 `uniqueItems`；因此 Schema 只声明数量和字符串长度，重复值检查由服务端工具强制执行。

`schema_validate` 仍然执行最终的逐字一致性校验，定位工具是降低错误率的前置步骤，不替代最终防线。

## 模型错误分类

| 错误 | 处理 | 原因 |
|---|---|---|
| 网络异常、超时 | 自动重试 | 通常是瞬时故障 |
| HTTP 408、409、425、429 | 自动重试 | 请求时序或限流问题 |
| HTTP 5xx | 自动重试 | Provider/代理暂时不可用 |
| 普通 HTTP 4xx | 直接失败 | 配置、认证或请求结构问题，重试通常无效 |
| Provider 返回非法 JSON 或错误工具调用 | 直接失败 | 违反本地 Agent 协议，需要修复实现或提示词 |

## 安全恢复

可重试错误会把 Run 转为 `retry_wait`，后台任务使用指数退避重新入队。超过最大尝试次数后，Run 和 Job 才进入 `failed`。

恢复策略为 `fresh_context_replay`：

- 从数据库重新读取原始材料、已批准记忆、Skills 和运行预算。
- 创建新的 Provider 上下文，从受约束流程开头重新执行。
- 保留已经持久化的审计事件、工具调用、Token 计数和错误记录。
- 不恢复或持久化模型隐式推理链。
- 工具调用继续使用幂等键，避免同一个调用重复产生业务副作用。

Worker 查询队列时也会寻找已经过期的 `running` 租约。新 Worker 接管后记录 `run.expired_lease_recovered`，再使用相同的干净上下文策略重跑。

## 当前验证

- 单元测试覆盖唯一/重复证据定位。
- 录制协议测试覆盖 `读取 -> 定位 -> 校验 -> 提交` 的 Responses API 回放结构。
- 单元测试覆盖 HTTP 503 的可重试分类。
- 后台任务测试覆盖重试排队与过期租约接管。
- 真实 `gpt-5.4-mini` 容器端到端运行已完成：5 条引用一次全部定位成功，草稿一次校验通过，Run 进入 `awaiting_user`。
- 该真实运行共执行 3 个业务工具调用，输入 9,000 Token、输出 3,947 Token；事件表中没有 `encrypted_content`。

## 后续优化

1. 用固定材料集记录单次运行的工具次数、Token、延迟、校验错误和覆盖率。
2. 对 `gpt-5.4-mini`、`gpt-5.4`、`gpt-5.5` 使用同一套评测材料。
3. 如果重新执行成本仍然过高，再设计只保存显式业务草稿、不保存 reasoning item 的阶段性恢复快照。
